## CAPTCHA: fixed empty-image bug

Symptom: comment CAPTCHA area was an empty box. Container rendered, but the
`background-image: url("/api/captcha/<id>")` returned 404 in the browser.

Root cause: `lib/comment-captcha.ts` kept challenges in a module-scoped
`new Map()`. Next.js compiles that module once per server layer (the
`react-server` condition used by server actions, and the plain Node condition
used by route handlers). Two module instances = two empty stores. The
`createCommentCaptcha` server action stored into instance A; `GET
/api/captcha/[id]` read from instance B -> always 404.

Proof: temporary RSC page `app/(public)/captcha-probe/page.tsx` called
`createCommentCaptcha()` (RSC layer) and printed same-layer read = true while
`GET /api/captcha/<id>` returned 404. Same-layer route `/api/captcha-debug`
returned a real 8 KB PNG, ruling out the canvas / font / API surface.

Fix: hoist the challenge `Map` onto `globalThis` (key
`__taekyarCaptchaChallenges__`) so the RSC and route-handler instances share
one store. Also:
- switched the comment-captcha client component from a CSS `background-image`
  div to a real `<img>` with `onError` -> "unavailable" fallback, so future
  fetch failures surface a message instead of a blank box.
- added `Content-Length` and `X-Content-Type-Options: nosniff` on the image
  response.
- removed the unauthenticated `/api/captcha-debug` route (it minted challenges
  without rate limits -> small DoS surface).

Changed files:
- `lib/comment-captcha.ts` - globalThis-backed store
- `app/api/captcha/[id]/route.ts` - extra response headers
- `components/blog/comments/comment-captcha.tsx` - <img> + onError fallback
- deleted: `app/api/captcha-debug/`, `app/(public)/captcha-probe/`

Verified: `node --experimental-strip-types captcha-flow-test.mts` -> 19/19
PASS. `npm run lint` -> clean. `npm run build` -> OK, `/api/captcha/[id]`
listed in the route map.

## CAPTCHA: rewrote to a static, always-fresh image endpoint

Replaced the per-id `GET /api/captcha/[id]` + `createCommentCaptcha` server
action with a single static endpoint `GET /api/captcha/image` that mints a
new challenge and a new image on every request. The challenge id never
reaches the browser; instead the response sets an HttpOnly `tc_captcha`
cookie carrying a random session token, and `submitComment` reads the
cookie on the server to find every live challenge for that session+IP.

Why: in this app the comment form and reply form render CAPTCHAs
side-by-side (the user can have both open at once), and a single-cookie
scheme broke that. The session-token + multi-live-challenge design keeps
both forms working while still binding verification to the cookie + IP.

Also:
- Renderer upgraded: WebP output (~3 KB vs ~8 KB PNG), gradient + ellipse
  background, straight + bezier interference strokes, ~40-90 speckle dots,
  short dashes, per-digit random font / size / rotation / skew / horizontal
  scale / synthetic-bold stroke / offset ghost.
- Font list: bundled Vazirmatn (guaranteed) + probed system families
  (Tahoma, Arial, Segoe UI, Times New Roman, Trebuchet MS, Verdana, Courier
  New). Each family is rendered against a PUA sentinel and a Persian digit
  to confirm it actually has the glyphs before being added to the pool.
- Answer hash now uses `crypto.timingSafeEqual` for constant-time compare.
- `lib/comment-rate-limit.ts` also moved to globalThis so the route layer
  and the RSC layer don't each carry a half-view of the counters.
- Deleted `app/api/captcha/[id]/route.ts` and the `createCommentCaptcha`
  server action.
- All CAPTCHA flow checks pass (26/26). Same-URL request returns 5 distinct
  images in a row. Response carries `Cache-Control: no-store, no-cache,
  must-revalidate, max-age=0, s-maxage=0, proxy-revalidate`, `Pragma`,
  `Expires: 0`, `Surrogate-Control: no-store`, `Last-Modified` epoch,
  `X-Content-Type-Options: nosniff`. No ETag -> no 304 path.

Changed files:

- `lib/comment-rate-limit.ts` (globalThis store)
- `lib/comment-actions.ts` (drop createCommentCaptcha, cookie-based verify)

## CAPTCHA package research (for next time someone asks)

Landscape: the only maintained self-hosted raster CAPTCHA generator on npm
is `captcha-canvas@3.4.0` (2025-10), which sits on `skia-canvas` and has
no documented way to register an external TTF (Persian digits will tofu).
`svg-captcha@1.4.0` (2019) is the popular one but outputs SVG, which
embeds the answer as `<text>` and ships the plaintext to the client --
unacceptable when the spec says "user should never receive the answer".
Everything else under "captcha" on npm is a third-party-service SDK
(reCAPTCHA, Turnstile, hCaptcha, Yandex, Friendly, CapSolver) or a
client widget. Custom render on top of `@napi-rs/canvas` (prebuilt
N-API, no postinstall compile, supports WebP) is the right call here.

## Notes for future CAPTCHA work

- Never store CAPTCHA (or any in-memory) state in a plain module-level
  variable that may be imported from both server actions and route handlers;
  use `globalThis` or an external store.
- For per-request dynamic images, plain `<img>` (not `next/image`) is correct
  - the optimizer would re-cache and re-expose stale challenges. Disable the
  `@next/next/no-img-element` lint rule with a comment explaining why.
- If you ever want to test font coverage at runtime, the PUA-vs-glyph
  probe (`renderGlyphProbe(family, digit)` vs `renderGlyphProbe(family, "\uE0FF")`)
  is reliable: fonts missing the digit fall back to the same `.notdef` box.

## Dashboard pagination: extracted shared component

The comments page (`app/dashboard/comments/page.tsx`) and posts page
(`app/dashboard/posts/page.tsx`) each had a near-identical prev/next + "X / Y
صفحه · N نتیجه" nav (the only diffs were the `buildHref` signature — comments
passed the active status filter — and which label object supplied the strings).

Extracted a single shared server component
`components/dashboard/shared/pagination-nav.tsx` -> `PaginationNav` with props
`{ currentPage, totalPages, total, buildHref: (page:number)=>string, labels }`.
`labels` is a `PaginationNavLabels` interface
(`prevPage/nextPage/pageInfoSuffix/resultsSuffix/title`); both
`COMMENTS_ADMIN_LABELS` and `POSTS_TABLE_LABELS` already satisfy it, so the
Persian strings stay in `data/dashboard/*.ts` per project convention.

Wiring: comments page binds status via `buildHref={(page) => buildHref(page,
statusFilter)}`; posts page passes `buildHref` directly. Removed the two local
components + their interfaces, and dropped the now-unused `ArrowRight`/`ArrowLeft`
imports (posts keeps `ArrowLeft` for the "new post" buttons).

Verified: `npx tsc --noEmit` clean; `eslint` on the 3 touched files clean.
(Note: the public `components/blog/pagination.tsx` `BlogPagination` is a
different numbered-chip design and was intentionally left alone.)
