### Radix dropdown: two non-obvious root causes (read from node_modules)
1. **RTL broken:** `@radix-ui/react-direction` `useDirection(localDir) => localDir || globalDir || "ltr"`.
   With no `DirectionProvider` and no `dir` prop, `rootContext.dir === "ltr"`, and `@radix-ui/react-menu`
   writes `dir: rootContext.dir` onto the real DOM nodes (`PopperPrimitive.Content` and
   `RovingFocusGroup.Root`). That `dir="ltr"` **overrides the inherited `<html dir="rtl">`**, so menu
   icons went left and labels left-aligned. Fix: default `dir="rtl"` on the `DropdownMenu` root wrapper
   (+ explicit `text-start` on item/label, which also neutralises the UA `<button>{text-align:center}`).
2. **8px layout shift:** `modal` defaults to `true` → `MenuRootContentModal` sets
   `disableOutsideScroll: true` → `ScrollLockWrapper = RemoveScroll` → `react-remove-scroll-bar`
   injects `body[data-scroll-locked]{margin-right:8px !important}`. Two aggravating factors:
   `getGapWidth` computes `innerWidth - documentElement.clientWidth`, and `html{scrollbar-gutter:stable}`
   already reserves that gutter, so the compensation is *pure* shift; and the lib always compensates on
   the **right** even in RTL, so the RTL layout (sidebar on the right) visibly shrank from the right.
   Fix: `modal={false}` → `MenuRootContentNonModal` (`disableOutsideScroll:false`) → no scroll lock at all.
   Focus behaviour is preserved: `FocusScope` is still rendered (`trapped:false`) and restores focus to
   the trigger via `onUnmountAutoFocus`; Escape / outside-click dismiss and roving focus + typeahead stay.
   Non-modal also drops `hideOthers()`, so the page is no longer `aria-hidden` from AT while open.
   Radix popper `align` is PHYSICAL (floating-ui `-start`/`-end`), not logical: with the account trigger
   at the visual LEFT in RTL, `align="end"` pushes the menu off-screen and relies on `shift`; the wrapper
   default is now `align="start"` (flush with the button's left edge).

### Sidebar top area (density)
`components/dashboard/layout/dashboard-sidebar.tsx`: header block `px-5 pb-4 pt-5` → `px-5 pb-2 pt-4`,

## CORRECTION — popper `align` is LOGICAL, not physical

The paragraph above claiming `align` is PHYSICAL is WRONG, and the `align="start"` value it justified
was itself the cause of the reported "dropdown is glued to the screen edge" bug.
`@floating-ui/core` `computeCoordsFromPlacement` ends with
`coords[alignmentAxis] += commonAlign * (alignment === "end" ? 1 : -1) * (rtl && isVertical ? -1 : 1)`,
with `rtl = platform.isRTL(el) = getComputedStyle(el).direction === "rtl"`. Measured by importing
`@floating-ui/core` in Node with a mocked platform (1280px viewport, 224px menu, trigger at x=32):

| rtl | align | menu.x | overflow |
| --- | --- | --- | --- |
| true | start | −42 | 42px off the LEFT edge → `shift()` clamps it to 0 (flush to the corner) |
| true | end | 32 | none (32px inset, i.e. the topbar's own `lg:px-8`) |
| false | start | 32 | none |
| false | end | −42 | 42px off the left edge |

## Request B — final UX polish

### 1. Dropdown spacing — `components/ui/dropdown-menu.tsx`
`align` `"start"` → `"end"` (opens inward, away from the left viewport edge) + `collisionPadding={12}`
as a narrow-viewport safety net. The account menu in `dashboard-user-menu.tsx` is the only consumer;
`select.tsx` uses `align="center"`, which is direction-symmetric and needs nothing.

### 2. Global dialog layout shift — `app/globals.css`
Root cause: `react-remove-scroll-bar` injects an un-layered `<style>` (appended to `<head>` last):

```css
body[data-scroll-locked] {
  overflow: hidden !important;
  padding-left: 0; padding-right: 0; margin-left: 0;
  margin-right: 8px !important;
}
body[data-scroll-locked] { --removed-body-scroll-bar-size: 8px; }
```

`html{scrollbar-gutter:stable}` already reserves the gutter, so this is pure double-compensation, and
the lib always compensates on the **right** with no RTL awareness — in RTL it drags the whole body
left. Global fix, in `@layer base` directly after the `html` rule:

```css
html body[data-scroll-locked] {
  margin-right: 0 !important; margin-left: 0 !important;
  padding-right: 0 !important; padding-left: 0 !important;
  --removed-body-scroll-bar-size: 0px !important;
}
```

Specificity (0,1,2) beats (0,1,1) **and** layered `!important` beats un-layered `!important`, so it
wins regardless of document order. The custom property needs `!important` because it is a *normal*
declaration. Nothing in `@radix-ui/*` consumes `--removed-body-scroll-bar-size` (grepped). This one
rule covers every Radix overlay — Dialog, AlertDialog, Sheet, Select, Popover — including
`ConfirmDialog` (9 call sites) and `sheet.tsx`, which is a Radix Dialog alias. `modal={false}` fixes
only menus; Dialog/Sheet cannot use it because Radix hardcodes `<RemoveScroll>`.

Why category-delete looked fine while comment-delete shifted: both use the identical `ConfirmDialog`;
the shift only appears when the page is tall enough to own a scrollbar.

Control experiment (headless Chrome `--headless=new`, RTL, 4000px page, `scrollbar-gutter: stable`),
measuring a flow element's rect:

| state | body margin-right | flow width | flow right |
| --- | --- | --- | --- |
| unlocked | 0px | 1249 | 1249 |
| locked, WITHOUT override | **8px** | **1241** | **1241** ← the bug |
| locked, WITH override | **0px** | 1249 | 1249 |

### The `dark:` variant leak — real but latent (important nuance)
`@custom-variant dark (…:not(:where(.theme-admin, .theme-admin *)))` exempts only `.theme-admin`, so
`dark:` utilities **do** still match inside `.theme-light`. They are mostly harmless because a scoped
custom property resolves **at the element** — `dark:bg-input/30` inside `.theme-light` reads the
*light* `--input`, not `.dark`'s. Real consequences are alpha drift (`bg-destructive/10`→`/20`,
`hover:bg-muted`→`/50`) and inconsistent hand-patching of `Button variant="outline"` (some call sites
add `bg-card border-border`, e.g. `error-content`/`not-found-content`/`mobile-menu`; `support-info.tsx`
does not). Carriers: `components/ui/{button,badge,input,textarea,select}.tsx` only. **No public
component depends on `dark:` utilities**, so adding `.theme-light` to the same `:not()` is surgical.
Caveat: `components/shared/section.tsx:14` `dark: "…"` is an object **key** (a tone name), not a
utility — false positive.

### Harness gotchas hit while verifying a Next dev server on Windows (reusable)
1. `npm run dev &` inside a Bash call **dies when the call returns** — the child is in the terminated
   process group. Use the Bash tool's `run_in_background: true` for the server, then curl in a
   *separate* call.
2. An `http_proxy` is set in this environment and **intercepts `localhost`**, yielding a bogus `502`.
   Always `curl --noproxy '*'`.
3. Windows `curl.exe` resolves `-o /tmp/x.html` as **`C:\tmp\x.html`**, while Git Bash `ls /tmp` looks
   in `%LOCALAPPDATA%\Temp` — the file "vanishes". Use a **relative** `-o` path inside the project and
   delete it afterwards.
4. `next dev` reports `Ready` before any route is compiled; the first request can take a while — give
   curl a generous `--max-time`.
